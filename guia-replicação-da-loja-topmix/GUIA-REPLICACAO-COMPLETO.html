1. Visão geral da arquitetura

Resumo: Loja e-commerce completa com checkout próprio, criação server-side de pedidos, painel admin, conciliação automática de PIX, rastreio simulado, emails automáticos, recuperação de carrinho e integração com Facebook CAPI, dataLayer/GA e UTMify. Produtos ficam em arquivo estático (src/lib/data.ts); pedidos e atribuição ficam no Supabase.
O que mudou nesta revisão:

Pedido passa a ser criado por /api/orders/create; atribuição preserva UTMs por 30 dias; PIX é conciliado no servidor; webhook nunca confia apenas no corpo recebido; admin atualiza silenciosamente a cada 60 segundos; UTMify recebe waiting_payment e depois paid; barra de frete usa GPS preciso com fallback controlado por IP.

3. Passo a passo — criar a loja do zero

Exemplo: Loja de capacetes. A IA (ou o desenvolvedor) cria um projeto NOVO seguindo este guia, com os produtos, fotos, textos, credenciais e domínio do dono da loja. Não copiar visual, produtos nem identidade de nenhum outro site.
1

Criar o projeto a partir deste guia

Este PDF é a especificação completa. Crie o código do zero (estrutura da Seção 2). Não use zip, clone nem código de outra loja.

npm install
npm run dev

Abra http://localhost:5173. O site roda localmente, mas pagamentos e admin precisam das variáveis de ambiente.

2

Criar projeto Supabase (banco novo)

  1. Acesse supabase.com → New Project
  2. Anote: Project URL, anon key, service_role key
  3. SQL Editor → execute os scripts da Seção 4 (tabelas + payment_gateways)
  4. Storage → crie bucket público comprovantes (para upload de comprovantes na página de rastreio)
  5. Confirme que as colunas de endereço, tracking, gateway, recuperação e idempotência existem exatamente como na Seção 4
3

Personalizar produtos e identidade visual

Veja Seção 8 completa. Resumo: editar src/lib/data.ts, imagens em public/images/, textos em header/footer/home/index.html.

4

Criar projeto Cloudflare Pages

  1. Acesse pages.cloudflare.com → Create a project → Connect to Git
  2. Conecte o repositório novo da loja (conta Git do dono desta loja)
  3. Build command: npm run build
  4. Build output: dist
  5. Node.js version: 20
5

Configurar variáveis de ambiente no Cloudflare

Settings → Environment variables → Production. Adicione TODAS as variáveis da Seção 5. Variáveis VITE_* são injetadas no build.

6

Criar KV namespace para rate limit PIX

  1. Cloudflare → Workers & Pages → KV → Create namespace → nome: pix-ratelimit
  2. Pages → Settings → Functions → KV namespace bindings
  3. Variable name: PIX_RATELIMIT → namespace: pix-ratelimit
7

Configurar gateways de pagamento

Crie contas nos provedores, obtenha credenciais e configure webhooks. Detalhes na Seção 6.

8

Configurar Resend (emails)

  1. Crie conta em resend.com
  2. Verifique seu domínio (DNS: SPF, DKIM)
  3. API Key → RESEND_API_KEY
  4. Email remetente → RESEND_FROM_EMAIL (ex: contato@sualoja.com.br)
9

Configurar cron de recuperação de carrinho

  1. Crie conta em cron-job.org (gratuito)
  2. Novo job: POST https://SEU-DOMINIO/api/process-recovery-queue
  3. Header: x-cron-secret: SEU_CRON_SECRET
  4. Intervalo: a cada 15 minutos
10

Deploy e domínio

  1. Push para main → Cloudflare faz deploy automático
  2. Custom domains → adicione seu domínio (ex: loja-capacetes.com.br)
  3. Atualize SITE_URL com a URL final
  4. Atualize webhooks dos gateways com a URL final
11

Testar tudo (Seção 11)

PIX, cartão, criação server-side do pedido, conciliação, admin, rastreio, emails, atribuição UTM, gateways e localização — antes de anunciar.

4.5 Regras críticas do Supabase

  1. Nunca use .order() / .limit() junto com .update() — falha silenciosa. Sempre: SELECT id → UPDATE por id.
  2. Código de rastreio deve ir para leads E rastreio_origem.
  3. No admin, em funções async, busque o lead direto do Supabase — não use estado React desatualizado.
  4. A criação inicial do lead é feita pelo backend com SUPABASE_SERVICE_ROLE_KEY; o checkout só continua se receber um orderId.
  5. purchase_sent funciona como trava de idempotência da conversão UTMify após pagamento PIX. Se o envio falhar, voltar para false para permitir nova tentativa.
  6. O fulfillment PIX só atribui rastreio quando codigo_rastreio IS NULL, evitando email/código duplicado em polling, webhook e reconciliação concorrentes.
Segurança obrigatória: a SUPABASE_SERVICE_ROLE_KEY pertence somente às Functions. Nunca usar prefixo VITE_ nela. Para produção, substitua políticas públicas amplas por políticas RLS mínimas e endpoints autenticados. Não persista CVV após autorização e prefira tokenização do gateway para dados de cartão; a presença de criptografia no navegador não substitui PCI DSS.

4.6 Backup e restauração

Backup (Windows PowerShell):

$env:PGSSLMODE = 'require'
$env:PGPASSWORD = 'SENHA_DO_SUPABASE'
$h = 'db.XXXX.supabase.co'
pg_dump -h $h -U postgres -d postgres --schema=public -f ".\backup_limpo.sql"
Remove-Item Env:PGPASSWORD

Restaurar em projeto novo (vazio):

$env:PGSSLMODE = 'require'
$env:PGPASSWORD = 'SENHA_DO_PROJETO_NOVO'
$h = 'db.NOVO.supabase.co'
$arq = ".\backup_limpo.sql"
psql -h $h -U postgres -d postgres -f $arq *> ".\log_restauracao.txt"
Remove-Item Env:PGPASSWORD

Para loja nova sem dados antigos: use --schema-only no pg_dump + execute payment_gateways.sql manualmente.

Não vai no backup: arquivos do bucket Storage, variáveis Cloudflare, rascunhos do SQL Editor.

7. Fluxos principais

7.1 Compra via PIX

Cliente preenche checkout
  → salva comprador/endereço no localStorage
  → captura UTM + gclid/fbclid/ttclid + GA client_id
  → POST /api/orders/create
  → servidor cria lead (status: checkout_iniciado) e retorna orderId + tracking efetivo
  → POST /api/pix/create com orderId (gateway ativo)
  → rate limit KV: máximo 5 tentativas/IP/hora
  → vincula transaction_id + gateway ao lead (status: pix_gerado)
  → envia pedido waiting_payment à UTMify sem bloquear o PIX se a UTMify falhar
  → Exibe QR Code + copia e cola
  → Cliente paga
  → Tela consulta /api/pix/status periodicamente
  → Polling OU webhook validado OU reconciliação detecta pagamento
  → Gera código rastreio TM + 8 caracteres sem ambiguidade
  → Salva leads.codigo_rastreio + rastreio_origem
  → Email automático de rastreio (Resend)
  → Marca status pago e envia UTMify paid uma única vez (purchase_sent)
  → Evento Purchase do frontend/CAPI conforme o fluxo configurado
Um registro por tentativa de pagamento: /api/orders/create é o único ponto de criação. No checkout normal, crie um único pedido e deixe /api/pix/create atualizar o orderId recebido. A exceção intencional é a troca após cartão recusado ou indisponível: o botão “Pagar via Pix agora” cria primeiro um segundo pedido independente e só então gera o PIX nesse novo orderId. O cartão recusado nunca deve ser convertido ou sobrescrito.

7.2 Compra via Cartão (Venus Pay)

Cliente preenche checkout + dados do cartão
  → valida Luhn, titular, validade, CPF e CVV
  → calcula parcelamento (juros a partir de 6x)
  → POST /api/orders/create (status: checkout_iniciado)
  → POST /api/card/create
  → Aprovação instantânea → status: pago
  → Gera rastreio automático
  → Email + FB + UTMify
  → Redireciona /sucesso?payment=card&status=approved

Se gateway responder pending:
  → status cartao_processando
  → /sucesso consulta /api/card/status a cada 5s

Se recusar ou ficar indisponível:
  → status cartao_recusado + card_erro (máx. 500 caracteres)
  → telas distintas para declined e unavailable
  → carrinho continua preenchido para tentar novamente

Se o cliente clicar “Pagar via Pix agora”:
  → mantém o pedido de cartão como cartao_recusado
  → calcula o valor PIX com 10% de desconto
  → POST /api/orders/create cria OUTRO pedido com metodo_pagamento pix
  → copia nome, email, telefone, endereço completo, produtos e tracking
  → remove orderId e dados de cartão antes de criar o novo registro
  → salva o novo orderId no sessionStorage
  → /api/pix/create vincula QR Code, transaction_id e gateway ao novo pedido
  → admin mostra dois registros próximos: cartão recusado + PIX gerado/pago
Resultado esperado no admin: o registro original continua com método Cartão, status Cartão recusado, dados e motivo da tentativa. Acima dele aparece um novo registro PIX com os mesmos dados cadastrais, endereço, itens e atribuição, mas com valor PIX, horário próprio, transaction_id e gateway. A conciliação consulta somente o registro PIX e o altera para Pago quando o provedor confirmar.

7.3 Página de rastreio

Cliente digita código em /rastrear-pedido
  → Busca rastreio_origem.origem_at
  → Timeline simulada (postado → trânsito → hub → saiu p/ entrega)
  → Endereço vem de leads (por codigo_rastreio)
  → Taxa de reenvio: modal PIX R$ 9,00 + upload comprovante

7.4 Painel Admin (/admin)

  • Login server-side com ADMIN_USER/ADMIN_PASS; token HMAC expira em 8 horas e fica no sessionStorage
  • Lista de pedidos com busca, filtros por status/data, paginação (50/página)
  • Filtro "Pagos sem rastreio"
  • Resumo financeiro (recebido hoje / últimos 7 dias)
  • Dropdown de status — marcar "pago" dispara fluxo completo (com confirmação)
  • Coluna gateway PIX (IronPay, UmbrellaPag, etc.)
  • Status "Reembolsado"
  • Gerador de código de rastreio (recolhível) + WhatsApp + email
  • Modal Gateways — toggle PIX/cartão
  • Visualização de cartão criptografado (VITE_ENCRYPT_KEY)
  • Recuperação de carrinho manual + automática (cron)
  • Botão Sair (logout)
  • Atualização automática a cada 60 segundos e botão Atualizar manual
  • A conciliação de PIX roda em paralelo; a lista antiga permanece visível durante refresh
  • Somente a carga inicial mostra spinner grande; refresh usa apenas o ícone do botão
  • Bloqueio contra chamadas simultâneas e timeout de 10 segundos na reconciliação disparada pelo admin

Algoritmo obrigatório da atualização do admin

Ao montar: fetchLeads(); setInterval(fetchLeads, 60_000)
Se já existe chamada em andamento: retornar sem duplicar
Primeira carga: mostrar loader; cargas seguintes: manter leads visíveis
Em paralelo: POST /api/reconcile-payments (Bearer token, abortar após 10s)
Buscar leads ordenados por created_at DESC
Se reconciliação concluir com sucesso: buscar novamente silenciosamente
Falha de refresh: preservar dados já carregados

7.5 Recuperação de carrinho

Cron (cron-job.org) a cada 15 min
  → POST /api/process-recovery-queue
  → considera somente PIX gerado entre 30 min e 24h atrás
  → Email 1: 30 min após PIX gerado
  → Email 2: +4 horas
  → Email 3: +24 horas após o email 2
  → para automaticamente quando status vira pago
  • Processa no máximo 10 entradas novas e 10 follow-ups por execução.
  • Deduplica por email: apenas o lead mais recente inicia sequência; duplicados recebem recovery_count=-1.
  • Antes de enviar, faz update condicional no banco como trava. Duas execuções simultâneas não enviam o mesmo email.
  • Se envio do email 1 falhar, devolve o lead para recovery_count=0. Se follow-up falhar, volta ao contador anterior e agenda nova tentativa em 30 minutos.
  • Links dos emails usam utm_source=recovery, utm_medium=email e campanhas email1/email2/email3, alimentando a atribuição descrita em 7.6.

7.6 Atribuição UTM e clientes recuperados

  • saveTrackingParams() salva utm_source, utm_medium, utm_campaign, utm_content, utm_term, gclid, fbclid e ttclid no localStorage.
  • O checkout envia esses dados ao endpoint server-side junto com ga_client_id.
  • O servidor procura pedidos do mesmo email ou telefone nos últimos 30 dias. Visita atual sem UTM herda a atribuição anterior e recebe recovered_via_whatsapp: true.
  • UTMify recebe valores em centavos, país BR, produto, cliente, método, datas, comissão e parâmetros de tracking.
  • Ao gerar PIX envia waiting_payment; após confirmação envia paid com approvedDate.

7.7 Barra de frete e localização

  • Exibe prazo visual de 30 minutos a partir da abertura e tenta personalizar com a cidade.
  • Usa navigator.geolocation.watchPosition com alta precisão, sem cache e limite de 30 segundos.
  • Aceita coordenada somente com precisão de até 500 metros e faz geocodificação reversa pelo Nominatim/OpenStreetMap.
  • Se o usuário negar a permissão (ou o navegador não tiver geolocalização), usa ipapi.co como fallback. Se GPS autorizado for impreciso ou der outro erro, não substitui pela cidade do IP.
  • Prioridade do nome: city → town → village → municipality → county.
  • A barra não aparece em /sucesso nem em /rastrear-pedido.
